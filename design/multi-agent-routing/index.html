    Design: Multi-agent routing (coordination layer)¶

    Status: Phase 1 & 2 DONE (router, CLI, MCP, HITL escalation, Routes UI, unified through trust_chain) · Owner: Max · Last updated: 2026-08-06 Roadmap context: agentic-governance-roadmap.md Phases 1–2 · Est. ~6–10 wk · Ships value at Phase 1 (local MVP)

    1. Problem & goal¶

    Sentrik governs a single agent's actions well (identity, trust, task scope, grants). But real agentic work is multiple specialized agents cooperating on one task — a "fix" agent hands off to a "test" agent, a low-trust agent escalates a risky change. Today there's no governed way to coordinate that: work crosses agent boundaries with no scope carry-over, no attribution, no gate.

    Goal: a governed routing/coordination layer so a task can move between agents with scope, trust, traceability, and audit intact at every hop — local- first, no hosted infra.

    2. Guardrail: what routing is (and isn't)¶

    Sentrik routes and gates; it does not run the agents. The routing layer decides which agent should handle work and whether a handoff is allowed, and records it — the host (Claude Code, Cursor, a CI script, an SDK loop) still invokes the agent. So: - Is: a decision + governance + ledger layer (match → authorize → record). - Is NOT: an execution runtime, a message broker/queue, or a remote service (remote/multi-tenant is the fleet's job — see roadmap).

    This keeps the surface small and the safety story tight.

    3. Foundation reused (nothing re-implemented)¶

    Capability Existing module Role in routing
    Who is acting core/agent_identity.py (AgentRegistry) Route targets + attribution
    May they core/agent_trust.py (check_agent_action) Gate the receiving agent per hop
    Detect running agent core/agent_detector.py Resolve "current agent"
    Task scope core/task_sessions.py (TaskSession) The unit carried across a handoff
    Temp elevation core/tool_grants.py Grant a receiver a scope for its leg
    Human gate core/approvals.py (create_approval_request) Escalation target (fail-closed)
    Attribution audit log (HMAC-signed) Every route/handoff/escalate recorded
    Agent surface mcp_server.py MCP tools Where route_task/handoff/escalate live
    Trust-capped delegation core/trust_chain.py (delegate_task) + task-delegate/task-chain CLI, delegate_task/check_delegation MCP Hierarchical parent→child sub-tasks with effective_trust = min(parent, max_trust) and chain-depth limits

    Reconciliation with the existing delegation primitive¶

    Sentrik already ships hierarchical, trust-capped delegation (trust_chain.delegate_task, surfaced via task-delegate/task-chain and MCP delegate_task/check_delegation). That is the privilege mechanism (a child can never exceed its parent's trust). Routing is the decision + coordination-ledger + escalation layer above it — "which agent, and is this hop allowed", recorded in a handoff ledger. They are complementary, not competing:

    • Now (Phase 1, shipped): agent_router uses an injectable store (better for tests + the future fleet) and creates the receiver session itself with narrow-only scope + a trust gate; escalation is fail-closed.
    • Unified (done): handoff's child-session creation now routes through trust_chain.delegate_task — delegate_task gained an optional store param (existing callers unchanged, still use the global store + bind_task); the router passes its own store. Trust-capping + chain-depth now live in exactly one place.

    4. Capabilities¶

    4a. Routing DSL¶

    Declarative rules mapping work → agent, stored in .sentrik/routes.yaml (checked in, team-shared). Matching mirrors the rules engine's applies_when so it's familiar and reuses that matcher:

    routes:
  - id: security-fixes
    when: { task_type: [fix], paths: ["src/auth/**", "**/*.sql"], min_trust: fix:low }
    to: security-fix-agent
    on_unavailable: escalate            # or: queue | reject
  - id: needs-tests
    when: { after: security-fixes, touched: ["src/**"] }
    to: test-writer-agent
  - default:
    to: human                            # nothing matched → escalate to human

    Router.match(task) returns the target agent + the matched rule. First-match wins; a default route always exists and defaults to human (fail-closed).

    4b. Handoff (message passing)¶

    handoff(to_agent, reason) moves an active TaskSession to another agent: 1. Verify the target exists (AgentRegistry) and check_agent_action permits the intended action at the target's trust level; if not → escalate. 2. Open a new TaskSession for the receiver, carrying intent, work_item_id, git_sha_at_start, and a scope no wider than the sender's declared_paths (intersection — a handoff can narrow scope, never widen it). 3. Link sessions (handoff_of / handoff_to) and write a Handoff ledger entry. 4. Audit-log the hop, attributed to the sending agent.

    4c. Escalation (fail-closed)¶

    escalate(reason, to?) when trust is insufficient, a route is unavailable, a scope check fails, or a hop count is exceeded. Targets, in order of preference: a higher-trust agent (if a route names one) or a human via approvals.create_approval_request — blocking the downstream action until resolved. Escalation never fails open: if no valid target resolves, the work stops and a human approval is created.

    5. Components to build¶

    • core/agent_router.py — Router (load rules, match, handoff, escalate, loop/hop guard) + Route/Handoff/RoutingRule models.
    • RouteStore / handoff ledger — local JSON (.sentrik/local/handoffs.json), same pattern as TaskSessionStore/ToolGrantStore.
    • MCP tools (in mcp_server.py): route_task(intent, task_type, paths), handoff(to, reason), escalate(reason), route_status.
    • CLI: sentrik route "<intent>" --type fix --path src/auth/** (dry-run shows the matched agent), sentrik handoffs [--session <id>], sentrik routes --validate.
    • Server API: GET /api/routes, GET /api/handoffs (read-only for the dashboard).
    • Dashboard: a Routes view — the routing rules + a live handoff graph (session → session edges), reusing the Vue page pattern.

    6. Data model (sketch)¶

    RoutingRule: id, when{task_type,paths,min_trust,after,touched}, to, on_unavailable
Handoff:     id, from_agent, to_agent, from_session, to_session, reason,
             status(pending|accepted|escalated|rejected), created_at, work_item_id
    TaskSession gains optional handoff_of / handoff_to links (additive; no migration — same store).

    7. Governance guarantees (the reason this belongs in Sentrik)¶

    • Every route/handoff/escalation is audit-logged and attributed to a named agent.
    • A handoff cannot widen scope (path intersection) or exceed the receiver's trust.
    • Loop/hop guard: max hops per task; a cycle → escalate to human.
    • Escalation fails closed to a human approval; never silently proceeds.
    • Work-item traceability (work_item_id) is carried the whole chain.

    8. Phasing (matches roadmap)¶

    1. P1 — Router MVP (local). ✅ DONE. core/agent_router.py (models, routes.yaml DSL + matcher, HandoffStore ledger, governed handoff with narrow-only scope + trust gate, fail-closed escalate, loop/hop guard) + route_task/handoff/ escalate MCP tools + sentrik route/routes/handoffs CLI + test_agent_router.py (12 tests). Local, zero infra.
    2. P2 — Escalation + traceability + UI. In progress.
    3. ✅ escalate opens a real approval (HITL gate): escalating to a human creates a pending ApprovalRequest (action_type=agent_escalation); the handoff carries its approval_id. Failed handoffs (trust/scope/loop) escalate to a human, not the failed agent.
    4. ✅ Work-item traceability: work_item_id is carried into the receiver session and every ledger entry across the chain.
    5. ✅ Dashboard Routes view — read-only page (rules + handoff ledger, escalation approval gates shown), GET /api/routes + GET /api/handoffs.
    6. ✅ Unified: handoff now creates its receiver through trust_chain.delegate_task (given an injectable store so the child lands in the router's store). Trust- capping (min(sender, receiver)) + chain-depth live in one place, and the receiver joins the delegation chain (visible to check_delegation/task-chain).

    9. Testing¶

    • Matcher: rule precedence, default→human, min_trust gating, after/touched chaining.
    • Handoff: scope intersection (narrow-only), trust rejection → escalate, session linking, audit entry written.
    • Escalation: no-valid-target → human approval created (fail-closed); loop/hop cap.
    • MCP + CLI round-trips; back-compat (routing absent → today's single-agent behavior).

    10. Open questions / non-goals¶

    • Invocation boundary: Sentrik returns the target + a scoped session; the host actually starts the agent. Confirm the handoff response shape the SDK/harness consumes (advisory vs enforced-at-commit).
    • DSL expressiveness: start minimal (task_type/paths/trust/after); resist a full rules language until real routes demand it.
    • Non-goals: execution runtime, message-queue infra, remote/multi-tenant routing (deferred to the fleet control plane).
    • Later (fleet): routes + handoff ledger move server-side and become cross-repo/tenant; the local DSL stays as the offline default.
