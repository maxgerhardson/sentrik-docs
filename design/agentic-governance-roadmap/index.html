    Roadmap: Agentic Governance Platform (routing + fleet)¶

    Status: Strategy / not started · Owner: Max · Last updated: 2026-08-05

    The strategic view of the two biggest roadmap bets — multi-agent routing (~6–10 wk) and the agent fleet / control plane (~3–4 mo) — how they fit together, what foundation already exists, and how to sequence them so each phase ships value on its own.

    1. The frame¶

    Sentrik today governs one agent, in one repo, on one machine: it can name an agent, decide what it's trusted to do, bind it to a task scope, and grant it time-limited tools. The platform play is to extend that same governance to many agents, coordinating across a task, across many repos and orgs — an agentic governance platform. Routing is the coordination layer; the fleet is the multi-tenant home. Same governance primitives, two axes of scale.

            ┌──────────────────────────────────────────────────────────┐
        │  AGENT FLEET / CONTROL PLANE  (multi-tenant, hosted)       │  ~3–4 mo
        │  hosted registry · tenancy · seats · policy dist · audit   │
        └──────────────────────────────────────────────────────────┘
                    ▲ (routing plugs in here at scale)
        ┌──────────────────────────────────────────────────────────┐
        │  MULTI-AGENT ROUTING  (coordination layer, local-first)    │  ~6–10 wk
        │  routing DSL · message passing · handoff · escalation      │
        └──────────────────────────────────────────────────────────┘
        ┌──────────────────────────────────────────────────────────┐
        │  FOUNDATION (exists today, local JSON, single-project)     │  shipped
        │  identity · trust · detection · task-sessions · grants ·   │
        │  compliance-orchestrator · org-dashboard                   │
        └──────────────────────────────────────────────────────────┘

    2. Foundation that already exists (build on, don't rebuild)¶

    Module Role Key limit today
    core/agent_identity.py (AgentRegistry) Named agents, scoped sk_agent_ creds (hashed) Local JSON, one project
    core/agent_trust.py Trust ladder + check_agent_action gating Config-file driven
    core/agent_detector.py Detects the running agent —
    core/task_sessions.py Intent binding + path-scope enforcement Local JSON
    core/tool_grants.py JIT time-limited scope grants + HITL Local JSON
    core/orchestrator.py (AgentOrchestrator) Parallel compliance agents (per pack) Scan workers, not task routing
    org-dashboard / core/org_dashboard.py Cross-repo compliance aggregation Single filesystem
    sentrik-portal.fly.dev Licensing + telemetry The hosted-infra seed
    MCP tools (mcp_server.py) bind_task, request_tool_grant, agent-check, … Per-install

    The through-line limitation: every store is a local JSON file, single project, single tenant. Both projects are, at their core, about lifting these primitives up a level of scale — routing lifts them across agents, the fleet lifts them across tenants/machines.

    3. Multi-agent routing (coordination layer)¶

    What it adds on top of the foundation: - Routing DSL — declarative rules for which agent handles which work (by task type, path, skill, trust level). Natural extension of the applies_when / policy patterns already in the rules engine. - Message passing / handoff — a task agent hands work to another (e.g. "security-fix agent" → "test-writer agent"), carrying task-session context and work-item traceability. - Escalation — on low trust, scope violation, or failed check, escalate to a higher-trust agent or a human (reuse tool_grants HITL + approvals).

    Reuse: identity (who), trust (may they), task-sessions (scope), grants (temporary elevation), audit log (attribution). Routing is the orchestration over these — it does not re-implement them.

    Not AgentOrchestrator: that dispatches compliance scan workers. Routing is about coordinating autonomous task agents. New module (core/agent_router.py + a routing-rules schema), but leaning on existing stores.

    Ships local-first — a single-project routing engine + DSL + MCP tools (route_task, handoff, escalate) is a self-contained, demoable differentiator with no hosted dependency.

    4. Agent fleet / control plane (multi-tenant home)¶

    What it adds: - Hosted registry & stores — promote AgentRegistry / TaskSessionStore / ToolGrantStore from local JSON to a server-backed, tenant-scoped store. - Tenancy & seats — org → project → agent hierarchy; per-org seat limits (the existing "seat management" TODO is a feature of this control plane, not a separate project). - Policy distribution — push trust config / grant policy / routing rules from the control plane down to installs (today they're per-repo files). - Fleet-wide audit aggregation — collect the HMAC-signed audit logs centrally; org-dashboard becomes a hosted, multi-tenant view. - Control-plane API + dashboard — extend sentrik-portal.fly.dev.

    The hard parts (why it's 3–4 mo): real multi-tenancy (isolation, authz), a hosted datastore (vs JSON files), agent↔control-plane auth (ties into the sentrik-owned-oauth and Auth0 device-flow work), and not breaking the local-first mode (installs must still work offline, syncing when connected).

    5. How they sequence¶

    They're layered but not blocking — routing ships local-first; the fleet is where routing (and everything else) scales. Recommended order, value-per-phase:

    1. Phase 1 — Routing MVP (local). agent_router.py + routing-DSL schema + route_task/handoff/escalate MCP tools + a dashboard "Routes" view. Ships the agentic differentiator with zero infra. (~4–6 wk of the routing budget.)
    2. Phase 2 — Routing: escalation + traceability. Wire escalation into the existing approvals/HITL + work-item links; handoff carries task-session context. (rest of routing budget.)
    3. Phase 3 — Control-plane skeleton. Extend the Fly portal: tenant model, hosted registry, agent auth (reuse device-flow/OAuth). Installs opt in to sync; local-first still works. (~6–8 wk.)
    4. Phase 4 — Seats + policy distribution. Per-org seat limits + enforcement; push trust/grant/routing policy down. Monetization lands here.
    5. Phase 5 — Fleet dashboard + audit aggregation. Hosted multi-tenant org-dashboard; central audit. Converge routing onto the control plane.

    Phases 1–2 are shippable and revenue-adjacent (differentiation) before any of the heavy infra in 3–5. If the goal is a demo/differentiator → do routing first. If the goal is enterprise monetization (seats) → the control plane is the gate.

    6. Key decisions & risks¶

    • Datastore for the control plane — Postgres on Fly vs a managed DB; must support tenant isolation + the existing JSON shapes (migration path from local).
    • Local-first invariant — installs must never require the control plane; sync is additive. Protects offline/air-gapped users and keeps the CLI honest.
    • Agent↔control-plane auth — depends on the OAuth/device-flow work (docs/design/sentrik-owned-oauth.md); don't build a third auth path.
    • Routing safety — a routing loop or a handoff that escapes task scope is a governance hole; escalation must fail closed (to human) not open.
    • Scope creep — routing can balloon into a full agent framework. Keep it a governance/coordination layer, not an execution runtime — Sentrik routes and gates; it doesn't run the agents.

    7. Effort summary¶

    Track Phases Est. Ships value at
    Multi-agent routing 1–2 ~6–10 wk Phase 1 (local MVP)
    Agent fleet / control plane 3–5 ~3–4 mo Phase 4 (seats)

    Recommendation: ship routing local-first (Phases 1–2) for a near-term agentic-governance differentiator, in parallel with scoping the control-plane datastore + tenant model (Phase 3) since that's the long pole. Seats (Phase 4) is the monetization milestone; gate the SaaS launch on it.

    8. Next step¶

    Pick the track to detail: a full design doc for routing (ready to start Phase 1) or the control plane (Phase 3 datastore/tenant design). This roadmap is the map; those are the build specs.
